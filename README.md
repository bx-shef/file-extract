# file-extract — сервис разбора файлов

> Last reviewed: 2026-11-17

Внутренний сервис: получает файл и возвращает его текст, а для таблиц — ещё и каждый лист
отдельным CSV. Им пользуются другие сервисы линейки (toolsai-mcp, позже импорт прайсов и
клиент-банк), чтобы разбор жил в одном месте, а не копиями в каждом продукте.

Логика разбора — та же, что в `ai-price-import`. Для разработчиков соседних сервисов — [docs/dev/README.md](docs/dev/README.md).

## Что умеет

| Формат | Как разбирается |
|---|---|
| TXT, CSV, TSV | чтение с определением кодировки: UTF-8, а если байты не UTF-8 — windows-1251 |
| PDF | `pdftotext -layout`, первые 500 страниц; если текста почти нет (меньше 32 непробельных знаков) — это скан, идёт в OCR |
| DOC, DOCX, ODT, RTF | LibreOffice → простой текст |
| XLS, XLSX, ODS | LibreOffice → каждый лист в свой CSV (разделитель — табуляция, UTF-8), до 64 листов |
| PNG, JPG, JPEG, TIF, TIFF, BMP, WEBP | Tesseract, языки rus+bel+kaz+eng; картинка больше 50 Мпикс (по заголовку PNG/JPEG/TIFF/BMP/WEBP) — отказ до OCR |
| PDF-скан | pdftoppm → PNG по страницам → Tesseract, до 30 страниц |

Со зрением (`VISION_URL`) у картинок PNG, JPG, JPEG и WEBP есть ещё описание от модели сервиса зрения
[toolsai-vision](https://github.com/bx-shef/toolsai-vision) (Qwen3-VL-4B): что на картинке и что
в ней главное. Описание идёт в начале `text` и отдельным полем `description` — раздел «Зрение» ниже.

После разбора текст чистится в одной точке: убираются управляющие символы (нулевой байт и
прочие), переводы строк и табуляция остаются. Если читаемого не осталось — ошибка `unreadable`.

## API

### `POST /v1/extract`

Порядок проверок: ключ → имя файла и формат → объявленный размер → место для приёма тела →
тело → кеш → место в очереди разбора → разбор.

- Тело — сырые байты файла.
- `X-File-Name` — имя файла, **обязателен**: по расширению выбирается способ разбора.
  Нелатинские имена передавайте через `encodeURIComponent`.
- `Authorization: Bearer <EXTRACT_API_KEY>`.

```bash
curl -s -X POST http://file-extract:3000/v1/extract \
  -H "Authorization: Bearer $EXTRACT_API_KEY" \
  -H "X-File-Name: $(node -p 'encodeURIComponent(process.argv[1])' 'Прайс.xlsx')" \
  --data-binary @Прайс.xlsx
```

Ответ `200`:

```json
{
  "text": "…",
  "sheets": [{ "name": "Лист1", "csv": "Товар\tЦена\n…", "rows": 12 }],
  "ocr": false,
  "truncated": false,
  "pages": 3,
  "cached": false,
  "kind": "office",
  "sha256": "…",
  "extractorVersion": "0.2.0-2"
}
```

- `sheets` — только для таблиц, иначе пустой массив.
- `pages` — только для OCR (число распознанных страниц).
- `kind` — `text` / `pdf` / `office` / `image`.
- `truncated: true` — текст (или листы) длиннее `MAX_TEXT_CHARS` и обрезан.
- `cached: true` — ответ из кеша.
- `extractorVersion` — версия разборщика, давшего результат (входит в ключ кеша).

Ошибки — JSON `{ "error": "<код>", "message": "<текст>" }`:

| Статус | Код | Когда |
|---|---|---|
| 400 | `bad_request` | нет `X-File-Name` или пустое тело |
| 401 | `unauthorized` | нет ключа или ключ неверный |
| 404 | `not_found` | нет такого адреса (в том числе старый `/extract`) |
| 405 | `method_not_allowed` | не тот метод (`/v1/extract` — только POST, `/health` — только GET) |
| 413 | `too_large` | файл больше `MAX_FILE_BYTES` (по `Content-Length` или по телу) |
| 415 | `unsupported` | формат не поддерживается |
| 422 | `unreadable` | после разбора нет читаемого текста |
| 422 | `too_complex` | больше 64 листов, лист CSV больше 50 МБ, больше 30 страниц скана, картинка больше 50 Мпикс, слишком большой вывод программы |
| 422 | `extract_failed` | программа разбора упала на этом файле (обычно битый файл) |
| 503 | `busy` | очередь полна (`MAX_QUEUE`) или не дождалась места за `QUEUE_TIMEOUT_MS` — повторите позже |
| 504 | `timeout` | разбор не уложился в `EXTRACT_TIMEOUT_MS` |
| 500 | `internal` | неожиданная ошибка сервиса |

**Временные и постоянные отказы** (для повторов у вызывающего, toolsai-mcp#83): `503` и `504`
— временные, повторять можно (с паузой); `400`, `401`, `413`, `415`, `422` — постоянные, повтор
того же файла даст тот же ответ. `500` — сбой сервиса, повторять осторожно.

На `401`, `413` и `503` сервис закрывает соединение после ответа, не дочитывая тело.
Клиент, закрывший соединение раньше ответа, прерывает свой разбор (и ожидание в очереди); в
журнале это `client_aborted`, ответа нет.

### `GET /health`

Без ключа. `200 {"ok": true, "version": "<версия разборщика>", "ready": true, "checks": {"programs": true, "cache": true}}`.
Главное — живость: ответ 200 и `version` как раньше (healthcheck образа ничего не потеряет). `ready` — готовность:
`programs` — pdftotext, pdftoppm, libreoffice, tesseract есть в PATH и исполняемы (запуска нет); `cache` — каталог
кеша доступен на запись или Redis отвечает (проверки — не дольше 2 с). Недоступный кеш разбор не останавливает
(файлы разбираются без кеша), но `ready` становится `false`. `GET /health?ready=1` — то же тело, но при `ready: false`
код 503: для проверок оркестратора. В теле только логические значения — путей и версий программ нет.

### `GET /metrics`

Нужен тот же ключ (`Authorization: Bearer`), что и разбору; без него — 401. Числа несекретны, но по ним видна нагрузка и
«такой файл уже присылали» (попадания кеша), поэтому открытым адрес не делаем. Текст Prometheus: `file_extract_requests_total{route,status}`
(503 — занят, 504 — не уложился, 499 — клиент ушёл), `file_extract_cache_hits_total`/`_misses_total` (доля попаданий =
hits / (hits + misses)), `file_extract_queue_depth`, `file_extract_slots_running`, `file_extract_bodies_inflight`,
`file_extract_memory_rss_bytes`, `file_extract_memory_peak_rss_bytes` (пик с запуска). Счётчики — с запуска процесса.
Имён файлов, текста и ключей в метках нет. Prometheus: `authorization: { credentials_file: … }` в `scrape_config`.

### POST /v1/convert?to=pdf|docx — сборка документа

Тело — HTML (UTF-8 без BOM, стили внутри, без внешних картинок: сети у контейнера нет) до 5 МБ,
заголовок `Authorization: Bearer <EXTRACT_API_KEY>`. Ответ 200 — байты файла (`application/pdf` или
Word `.docx`). Очередь, таймаут и потолок одновременных тел — общие с разбором; кеша нет. Сборка —
LibreOffice Writer (`--infilter=HTML (StarWriter)`), профиль — тот же, что у разбора. Клиент —
shef.cowork (`disk_doc_build`, КП помощника).

HTML сперва проверяется и пересобирается (`src/htmlGuard.ts`): LibreOffice получает не присланный
текст, а чистый HTML в одной записи (комментарии и повторы атрибутов отброшены). Картинки — только
`data:image/png|jpeg|gif;base64,…`: формат определяется по сигнатуре, размеры — по заголовку, все
картинки документа вместе — не больше 50 Мпикс. Ссылки в документе — текстом: `<a>` и `href`
отбрасываются, текст остаётся.

Ошибки — JSON `{ "error": "<код>", "message": "<текст>" }`:

| Статус | Код | Когда |
|---|---|---|
| 400 | `bad_request` | нет `to` или не `pdf`/`docx`; пустое тело |
| 400 | `unsafe_html` | HTML не собирается: не UTF-8 или BOM; вложенные документы, формы и скрипты (iframe, object, embed, link, base, script, svg, form…); `<meta>` кроме `charset="utf-8"`; `@import`; адрес в `src` и подобных атрибутах или в `url()` не `data:image` PNG/JPEG/GIF; картинки больше 50 Мпикс; необычное имя тега или атрибута, незакрытый тег, комментарий или кавычка. В `message` — причина, без содержимого документа |
| 401 | `unauthorized` | нет ключа или ключ неверный |
| 413 | `too_large` | HTML больше 5 МБ |
| 422 | `extract_failed` | LibreOffice не собрал документ |
| 422 | `too_complex` | готовый документ больше 20 МБ |
| 501 | `not_implemented` | исполнитель сборки не подключён (в образе подключён всегда) |
| 503 | `busy` | очередь полна (`MAX_QUEUE`) или не дождалась места за `QUEUE_TIMEOUT_MS` |
| 504 | `timeout` | сборка не уложилась в `EXTRACT_TIMEOUT_MS` |

## Настройки (env)

| Переменная | По умолчанию | Что значит |
|---|---|---|
| `EXTRACT_API_KEY` | — | общий ключ вызова, **обязателен**, не короче 16 знаков. Без него сервис не стартует (кроме `NODE_ENV=test`) |
| `HOST` | `127.0.0.1` | адрес, на котором слушает сервис. В образе Dockerfile задаёт `0.0.0.0` |
| `PORT` | `3000` | порт внутри контейнера |
| `MAX_FILE_BYTES` | `20971520` (20 МБ) | потолок размера файла |
| `MAX_TEXT_CHARS` | `2000000` | потолок текста в ответе (и отдельно — листов) |
| `MAX_CONCURRENCY` | `2` | сколько файлов разбирается одновременно |
| `MAX_QUEUE` | `8` | сколько запросов может ждать места; сверх — сразу `503`. Разборы + очередь — столько тел (до `MAX_FILE_BYTES`) одновременно в памяти |
| `QUEUE_TIMEOUT_MS` | `60000` | сколько файл может ждать места |
| `EXTRACT_TIMEOUT_MS` | `300000` | потолок времени на файл (5 минут — OCR 30 страниц); по нему дочерние процессы убиваются |
| `REDIS_URL` | — | задан — кеш в Redis |
| `CACHE_DIR` | `/tmp/file-extract-cache` | кеш на диске, если Redis не задан |
| `CACHE_MAX_BYTES` | `268435456` (256 МБ) | потолок дискового кеша; сверх — вытесняются записи, истекающие раньше |
| `VISION_URL` | — | база OpenAI-совместимого API сервиса зрения, например `http://vision:8080/v1`: http(s), без логина и пароля, запроса и якоря; пусто — картинки только OCR |
| `VISION_API_KEY` | — | ключ сервиса зрения (`API_KEY` из `.env` toolsai-vision); с `VISION_URL` обязателен |
| `VISION_MODEL` | `vision` | имя модели в запросе; входит в ключ кеша |
| `VISION_TIMEOUT_MS` | `150000` | потолок на очередь зрения и ответ; меньше `EXTRACT_TIMEOUT_MS` (зрение идёт параллельно и худший случай запроса не растёт), иначе ошибка запуска |
| `VISION_MAX_TOKENS` | `400` | потолок длины описания в токенах |

Неверное число в переменной — ошибка запуска, а не молчаливое умолчание.

## Зрение — описание картинок

Включается переменными `VISION_URL` и `VISION_API_KEY`. Сервис зрения — [toolsai-vision](https://github.com/bx-shef/toolsai-vision) (образ `ghcr.io/bx-shef/toolsai-vision`; его README — «Установка у клиента»). Он слушает `127.0.0.1:8093`, имя модели `vision`.

- **Что происходит.** Картинка получила место разбора — и идёт в OCR и, параллельно, в сервис зрения (`data:`-адрес
  внутри запроса). Ответ: `text` = «Описание картинки: …» + «Текст с картинки: …», поле `description` — само описание.
  Места разбора не дали (503) — зрение и не начиналось.
- **Место разбора зрение не держит.** У зрения своя очередь: одна картинка в работе, ждут не больше двух и не дольше
  половины `VISION_TIMEOUT_MS` (он на очередь и ответ вместе) — получившая место успевает ответить. Лишняя картинка —
  сразу без описания. Пока модель думает десятки секунд, место разбора уже отдано следующему файлу, а картинка,
  ждущая только зрения, не занимает место тела в памяти (`MAX_CONCURRENCY` + `MAX_QUEUE`) — другие файлы не получают 503.
- **Что уходит в зрение.** Формат — по байтам файла, не по имени: PNG, JPEG, WEBP. TIF, TIFF, BMP, «.png» с чужими
  байтами и картинки больше 50 Мпикс (как у OCR) зрение не берёт — у них только OCR. Ответ зрения читается не
  больше 64 КБ; управляющие символы и знаки направления текста из описания вычищаются.
- **Сбой зрения — не сбой разбора.** Сервис не ответил, ответил ошибкой, очередь зрения занята или не уложились в
  `VISION_TIMEOUT_MS` — картинка остаётся с текстом OCR, в журнале — событие `vision_failed` с причиной
  (`timeout`, `busy`, `http_503`, `network`…), без текста и имён; формат, размер и уход клиента — не сбой, в журнал не идут.
  **Такой ответ не кешируется**: следующий запрос той же картинки снова спросит зрение. Отказ по формату и размеру кешируется — те же байты дадут тот же отказ.
- **Фото без текста** со зрением — не ошибка `unreadable`: в ответе описание и «Текста на картинке не найдено.».
  Зрение не ответило по временной причине (занято, таймаут, сеть) — 503 `busy`: повторите позже, а не «нет текста».
  Отказ по формату или размеру (зрение такую картинку не берёт) — `unreadable`, как без зрения.
- **Время.** Описание — от 20 с на снимок телефона до 1,5 мин на снимок экрана на 4 ядрах (замер в toolsai-vision, docs/bench-vision).
  Потребитель ждёт ответа дольше обычного; shef.cowork при долгом разборе отвечает «ещё разбирается» и
  повторяет — результат к тому времени лежит в кеше.
- **Сеть.** Зрение — в своей внутренней сети `vision` только между file-extract и контейнером зрения
  (`docker-compose.example.yml`): соседи file-extract по сети `extract` к зрению не ходят, а зрение — к
  file-extract. Адрес — по имени: `VISION_URL=http://vision:8080/v1`. Наружу сам сервис зрения не ходит не из-за сети
  (у него есть и своя `default` — для весов), а потому что точка входа toolsai-vision направляет исходящие запросы
  llama-server на закрытый порт (его `docs/API.md`): образ зрения — только toolsai-vision.
  Контейнер зрения из другого проекта
  compose (toolsai-vision) подключается к ней как к внешней — `docker-compose.override.yml` рядом с его
  `docker-compose.yml`:

  ```yaml
  services:
    vision:
      networks: [default, file-extract-vision]
  networks:
    file-extract-vision:
      external: true
      name: <проект file-extract>_vision
  ```
- **Модель.** `VISION_MODEL` — имя в запросе, оно же входит в ключ кеша. Сменили модель за тем же именем
  (toolsai-vision) — сутки кеш отдаёт описания прежней. Чтобы сразу: перезапустить file-extract
  (кеш в tmpfs пропадёт) или сменить `VISION_MAX_TOKENS` — он тоже в ключе.

## Кеш

- Ключ — sha256 от версии разборщика, способа разбора, расширения файла (одни байты под `.xls`
  и `.doc` LibreOffice разбирает разными фильтрами), `MAX_TEXT_CHARS` (обрезка — до кеша), у картинок —
  зрения (модель, версия запроса, потолок описания; включили зрение — картинка разбирается заново) и
  sha256 файла. Сменилась логика
  разбора — поднимается `EXTRACTOR_VERSION` (`src/config.ts`), и старый кеш больше не отдаётся.
- Срок — **ровно 24 часа и не дольше**: в тексте персональные данные. Чтение срок не продлевает.
- Кешируется только успех; картинка, у которой зрение не ответило (таймаут, сеть, «занято», пустой ответ), — не кешируется.
- Redis держит срок сам (`SET … EX 86400`). На диске срок записан в mtime файла; просроченное
  удаляется при чтении и раз в час.
- Недоступный кеш и испорченная запись — не отказ: файл просто разбирается заново.
- Дисковый кеш ограничен `CACHE_MAX_BYTES` (tmpfs — это память контейнера).
- ⚠ Не подключайте общий Redis MCP-сервера: у него AOF на диск, `noeviction` и 64 МБ — кеш с
  персональными данными записался бы на диск и выдавил бы токены. Только свой Redis без тома.

## Изоляция и лимиты

Это чужие файлы, а LibreOffice и парсеры PDF исторически уязвимы.

⚠ **Сетевая изоляция и лимиты действуют только при запуске по примеру compose
(`docker-compose.example.yml`) или по `docker run` ниже** — сам код их не обеспечивает. Лимита
памяти на отдельный процесс разбора нет: граница — лимит памяти контейнера.

```bash
docker run --rm --network none --memory 1536m --cpus 1 --pids-limit 256 \
  --cap-drop ALL --security-opt no-new-privileges \
  --read-only --tmpfs /tmp:size=1g,noexec,nosuid,nodev \
  -e EXTRACT_API_KEY=… ghcr.io/bx-shef/file-extract:<sha коммита>
```

(`--network none` — для разовой проверки; в стеке — внутренняя сеть `internal: true`.)

Что делает сам сервис:

- слушает `127.0.0.1`, пока `HOST` не задан (в образе — `0.0.0.0` для внутренней сети);
- не больше `MAX_CONCURRENCY` разборов и `MAX_QUEUE` ожидающих; столько же тел одновременно в
  памяти; число соединений ограничено (`maxConnections`);
- таймаут на файл и на каждый процесс (90 с); по таймауту и при уходе клиента убивается вся
  группа процессов (LibreOffice порождает `soffice.bin`), она же добивается после завершения;
- программы разбора получают окружение без секретов (белый список: `PATH`, локаль, шрифты…), а
  `HOME`, `XDG_*`, `TMPDIR` и рабочий каталог — свой временный каталог разбора;
- LibreOffice — со свежим профилем на каждый файл, в профиле: уровень безопасности макросов 3 и
  запрет макросов, запрет загрузки ссылок из документа (`BlockUntrustedRefererLinks`), запрет
  обновления внешних связей в Calc и Writer. `--safe-mode` не используется: он подменяет профиль
  временным и отбрасывает эти настройки (проверено вживую — с ним внешняя картинка снова
  запрашивается). Сеть этим закрыта не до конца — граница сети всё равно контейнер;
- бомбы: картинка больше 50 Мпикс — отказ до OCR по заголовку файла; лист CSV больше 50 МБ —
  отказ до чтения; `pdftotext` читает не больше 500 страниц; вывод программы — до 64 МБ;
- путь CSV из вывода LibreOffice принимается, только если он внутри своего рабочего каталога;
- каждый файл — в своём временном каталоге (`mkdtemp`), каталог удаляется в `finally`;
- образ работает не от root (`USER 1000:1000`), базовый образ закреплён по digest.

## Персональные данные

- В журнал пишется **только**: способ разбора (`kind`), размер, время (`ms`) и ожидание в
  очереди (`queueMs`), первые 12 знаков sha256, признак кеша, код ошибки и для `500` — класс
  системной ошибки (`errorClass`, например `ENOSPC`, без текста). **Никогда** — имя файла и
  текст. Поля журнала закрыты типом, набор ключей держит тест.
- Служебные события журнала: `start` (с `version`), `cache_sweep` (с `removed`),
  `cache_sweep_failed`.
- Текст ошибки, который уходит вызывающему, не содержит имени файла и содержимого.
- Файл хранится только на время разбора; результат — в кеше не дольше 24 часов.

## Запуск

```bash
pnpm install
pnpm typecheck
pnpm test
EXTRACT_API_KEY=$(openssl rand -hex 32) pnpm start   # нужны pdftotext, libreoffice, tesseract в PATH
```

В Docker:

```bash
docker build -t file-extract .
docker run --rm --read-only --tmpfs /tmp -e EXTRACT_API_KEY=$(openssl rand -hex 32) file-extract
```

Интеграционный тест (`tests/integration.test.ts`) гоняется на настоящих программах, если
`soffice` и `pdftotext` есть в `PATH`; в CI их нет — он пропускается.

Пример для compose — `docker-compose.example.yml`. Образ публикуется в
`ghcr.io/bx-shef/file-extract` на каждый push в `main` с тегом sha коммита (и `latest`); в
compose указывайте тег sha.

В образе PID 1 — `tini`: он подбирает осиротевшие процессы, которые LibreOffice запускает на
каждый документ (`gpgconf`, `gpg`, `gpgsm`); без него контейнер упирается в `pids_limit`.
